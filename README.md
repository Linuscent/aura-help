# Aura Help

User-facing help and documentation for Linuscent Aura.

## Documentation stack

The site is built with **Astro + Starlight**. All documentation content lives in a single source of truth:

```text
src/content/docs/
```

Edit the Markdown/MDX files in `src/content/docs/` directly. There is no separate documentation source directory.

## Documentation structure

```text
src/content/docs/
├── index.mdx
├── getting-started/
├── products-and-releases/

├── sbom/

```

## Local development

```bash
npm ci
npm run dev      # start the local dev server
npm run build    # production build
npm run check    # run astro check
```

Use Node.js 24 (also used in CI). Open the local site at
<http://localhost:4321/>. The production site is deployed to
<https://aura.docs.linuscent.com/> by `.github/workflows/deploy.yml`.
The site is served from `/`, with the GitHub Pages custom domain recorded in
`public/CNAME`. Configure the same domain in the repository's Pages settings
and point its DNS record at `linuscent.github.io`.

## Content conventions

Each documentation page:

- includes Starlight-compatible YAML frontmatter;
- defines a `title` and `description`;
- uses `sidebar.order` for predictable autogenerated navigation;
- starts page content below heading level 1 because Starlight renders the page title;
- uses root-relative internal route links (for example
  `/getting-started/what-is-aura/`) instead of source `.md` links;
- ends with a **Related articles** section;
- uses the current Aura term **Product** rather than the older **Project** terminology;
- avoids documenting unavailable or unconfirmed features as active functionality.

## Product documentation principles

Documentation should:

- stay task-oriented;
- reflect terminology shown in the current Aura interface;
- distinguish security findings from final risk decisions;
- avoid claiming that Aura itself certifies CRA compliance;
- avoid documenting unfinished functionality until it is available;
- preserve traceable links between products, releases, SBOMs, findings, evidence, and compliance workflows.

The splash homepage is an exception to article-only conventions such as
`sidebar.order` and **Related articles**. Sidebar groups and their ordering are
configured in `astro.config.mjs`; article ordering uses frontmatter.

Do not publish credentials, customer data, local filesystem paths, or internal
working notes. Use synthetic examples and verify product claims before publishing.

## Design system

[`DESIGN.md`](DESIGN.md) records the Linuscent Aura design system and its
light/dark tokens, typography, component states, and accessibility rules.
`src/styles/theme.css` defines the tokens and maps them to Starlight;
`src/styles/docs.css` applies the shared component treatments. Fonts are
self-hosted using Fontsource packages, with no third-party font requests.

The first visit defaults to dark. Reader choices of light, dark, or automatic
are preserved, including a mobile appearance selector on the homepage.

## Search engines and social previews

- Article frontmatter supplies unique page titles and descriptions. Starlight
  generates canonical URLs, sitemap links, and the XML sitemap for the custom domain.
- Routes use trailing-slash canonical URLs. The homepage uses the `website`
  Open Graph type; guides use `article`.
- `src/components/Head.astro` adds Open Graph and Twitter image metadata, crawler
  directives, and a JSON-LD graph for the publisher, website, page, and breadcrumbs.
  The 404 page and drafts are marked `noindex`; no modification dates are fabricated.
- `public/robots.txt` permits crawling and advertises the sitemap. The site is
  statically rendered and uses local fonts and images, so content does not rely
  on a crawler executing JavaScript.
- `public/social/aura-docs.png` is a local 1200×630 social card built from the
  official wordmark and the existing homepage copy. Regenerate it with
  `npx playwright install chromium`, then `npm run generate:og`.

`npm run build` automatically runs `npm run check:seo`. The checker validates all
generated pages for unique metadata, canonical URLs, one h1, JSON-LD, social-card
dimensions, sitemap coverage, crawl directives, alt attributes, and local links
and fragments. This also gates PR builds and deployment builds. Run the checker
separately only after building `dist/`.

After deployment, the site owner must verify `aura.docs.linuscent.com` in Google
Search Console and Bing Webmaster Tools and submit
`https://aura.docs.linuscent.com/sitemap-index.xml`. DNS, HTTPS, production status
codes, field Core Web Vitals, indexing, and rankings need live monitoring; a local
build cannot establish them. New `noindex` pages must also be excluded from the
sitemap—the checker intentionally rejects mismatches.

## Documentation MCP server

[`@stellayazilim/mcp-starlight`](https://github.com/stellayazilim/mcp-starlight)
generates `dist/mcp-catalog.json` and `dist/mcp-catalog.version.json` during
`npm run build`. GitHub Pages publishes both files with the site; no hosted
MCP process or deployment changes are needed. The catalog contains documentation
from `src/content/docs/`, not live Aura workspace data.

After deploying, add this configuration to an MCP client that supports local
stdio servers (Node.js and npm are required):

```json
{
  "mcpServers": {
    "aura-help": {
      "command": "npx",
      "args": [
        "-y",
        "@stellayazilim/mcp-starlight@0.2.1",
        "https://aura.docs.linuscent.com"
      ]
    }
  }
}
```

The client runs the server locally, which fetches the published catalog and
provides `search_docs`, `get_doc`, and `list_docs`. The version file lets it
detect updated documentation. CI builds use `GITHUB_SHA` as the revision;
local builds use a content hash.

To test a local build without deploying, configure the client to run
`npx -y @stellayazilim/mcp-starlight@0.2.1 ./dist/mcp-catalog.json` from the
repository root (or pass an absolute catalog path).

The extension currently declares an Astro 5 peer dependency. `package.json`
scopes an override to this package to use the site's Astro 7 dependency,
without relaxing peer checks globally. A local declaration file supplies its
missing integration types. Recheck both workarounds when upgrading the extension.

## AI-assisted development

Repository guidance lives in [`AGENTS.md`](AGENTS.md). [`opencode.json`](opencode.json)
configures these MCP servers using the OpenCode V2 format:

- **Astro Docs**: the official remote documentation search server.
- **Playwright**: local, headless browser automation with isolated sessions.
  Automatically named artifacts go into the ignored `.playwright-mcp/` directory.

Start OpenCode from the repository root and run `opencode mcp list` to check
connections. Playwright is downloaded through `npx` on first use and requires
network access and an installed browser. If it reports a missing Chrome browser,
install it with `npx playwright install chrome` (Linux may also need system
dependencies). Neither configuration contains credentials; do not use real
customer accounts during browser checks.

## Pull requests and commits

PR titles and every new commit message must follow
[Conventional Commits](https://www.conventionalcommits.org/en/v1.0.0/):

```text
docs(sbom): clarify supported upload formats
fix(navigation): correct the getting started link
ci: validate documentation changes
```

Allowed types: `build`, `chore`, `ci`, `docs`, `feat`, `fix`, `perf`, `refactor`,
`revert`, `style`, `test`. A scope is optional; append `!` before the colon for
breaking changes. Merge messages are not exempt: use a conventional merge message
or prefer squash/rebase merging, retaining a conventional final message.

Validate locally:

```sh
printf '%s\n' 'docs: clarify setup instructions' | npm run lint:commit
npm run lint:commit -- --from <base-sha> --to HEAD
npm run check
npm run build
```

GitHub Actions checks PR titles on edits, all commits introduced by a PR, and
commits pushed to any branch. New branches check history not already on another
remote branch. Existing history is not rewritten. A separate workflow runs Astro
checks and a production build for PRs and pushes to `main`.

To block merges on failure, repository administrators must mark **PR title and
commit messages** and **Astro check and build** as required status checks in a
branch ruleset. Workflow files alone do not enable branch protection.
